# Kimono v1 Spec

> **[SUPERSEDED]** Superseded by [v2 spec](./20260421-v2-spec.md) as of 2026-04-21. Kept for history — do not implement against this document.

> A multi-repo aggregator for AI-assisted development with Claude Code.

Kimono wraps multiple repositories into a single workspace with shared context, worktree-based development, and generated Claude Code configuration. Developers get monorepo-like AI context while keeping polyrepo independence for CI/CD, deployment, and ownership.

---

## 1. Core Concepts

### The Workspace

A kimono workspace is a git repo that acts as an orchestrator. It contains:

- **Config** (`.kimono/config.yml`) — registry of repos with metadata
- **Apps** (`apps/`) — read-only clones, always on default branch. The source of truth AI agents read from.
- **Worktrees** (`.worktrees/`) — all active development happens here. One worktree per repo per feature branch.
- **Generated context** (`CLAUDE.md`, `.claude/`) — auto-generated Claude Code configuration

### Read-Only Master Pattern

`apps/` is never directly modified. It stays on the default branch and serves as a clean reference. AI agents read cross-repo context from `apps/` while writing code in `.worktrees/`. Hooks enforce this.

### Worktree-Based Development

All feature work uses git worktrees. A developer working on "payments" across backend and frontend gets:

```
.worktrees/
  backend--feature-payments/
  frontend--feature-payments/
```

Each worktree is a full checkout. The developer (or AI agent) works in the worktree, commits, pushes, and opens PRs from there. The `apps/` clone stays clean.

### Feature Workspaces

The killer abstraction: a "feature" spans multiple repos. `kimono wt feature payments backend frontend` creates coordinated worktrees across repos with a single command. Cleanup is similarly unified.

## 2. Tech Stack: Rust

### Why Rust

| Concern | Bash | Rust |
|---------|------|------|
| **YAML parsing** | Requires `yq` dependency or hand-rolled parser | `serde_yaml` — typed, validated, ~50 lines |
| **Config validation** | Silent failures on bad config | Compile-time types + serde errors with line numbers |
| **CLI UX** | Manual `--help`, manual arg parsing | `clap` — subcommands, help, completions, colors for free |
| **Distribution** | curl a script or copy files | Single binary: `cargo install`, `brew install`, GitHub release |
| **Cross-platform** | macOS/Linux native, Windows needs WSL | Compiles natively for all three |
| **Interactive prompts** | `read -p` (limited) | `dialoguer` — select, multiselect, confirm, input with validation |
| **File generation** | Heredocs / echo | `tera` or `askama` templates — logic, loops, conditionals |
| **Testing** | bats (painful) | Built-in test framework, integration tests |
| **Git operations** | `git` commands via shell | `std::process::Command` calling `git` (same thing, just wrapped) |
| **Time to v1** | ~3 days | ~2 weeks |
| **Maintenance** | ofmono showed: scripts hit a wall at 5 files | Scales cleanly with modules |

**The tipping point**: `.kimono/config.yml` is a rich nested config (repos with metadata, dependency arrays, command maps). Parsing this reliably in bash requires a `yq` dependency — at which point you're adding a non-trivial external dependency to a "simple bash tool" anyway. Rust gives validated parsing, a single binary, and no rewrite later.

**Decision: Rust.** Single binary, typed config, proper CLI UX from day one.

### Key Rust Crates

| Crate | Purpose |
|-------|---------|
| `clap` (derive) | CLI argument parsing, subcommands, help generation |
| `serde` + `serde_yaml` | Config deserialization and validation |
| `dialoguer` | Interactive prompts for `kimono init` |
| `console` + `indicatif` | Colors, spinners, progress bars |
| `tera` | Template engine for generating CLAUDE.md and agent files |
| `which` | Verify `git` is available |
| `dirs` | XDG-compliant config/cache paths |

Git operations use `std::process::Command` to call `git` directly — no libgit2 dependency. This keeps behavior identical to what users expect from git.

### Tera Template Engine

[Tera](https://keats.github.io/tera/) is a Jinja2/Django-style template engine for Rust. Kimono uses it to generate all Claude Code context files from `.kimono/config.yml` metadata. Templates are compiled into the binary (via `include_str!`) so there are no external template files to distribute.

**Why Tera over alternatives:**
- **vs. `askama`** — askama is compile-time (templates checked at build), but Tera's runtime rendering is needed because templates depend on user config that varies per workspace.
- **vs. `handlebars`** — Tera has richer control flow (if/elif/else, for/else, macros) and filters, closer to what's needed for generating structured markdown.
- **vs. raw `format!`/string concatenation** — templates become unmaintainable once they include loops, conditionals, and nested structures. CLAUDE.md generation has all three.

**Core syntax:**

```jinja2
{# Variables #}
{{ workspace.name }}
{{ repo.description }}

{# Filters — transform values inline #}
{{ name | upper }}
{{ tech_list | join(sep=", ") }}
{{ description | default(value="No description") }}
{{ name | capitalize }}

{# Conditionals #}
{% if repo.depends_on | length > 0 %}
Depends on: {{ repo.depends_on | join(sep=", ") }}
{% endif %}

{# Loops #}
{% for name, repo in repos %}
- **{{ name }}**: {{ repo.description }}
{% endfor %}

{# Loop with else (when collection is empty) #}
{% for dep in repo.depends_on %}
- {{ dep }}
{% else %}
No dependencies.
{% endfor %}

{# Macros — reusable template fragments #}
{% macro repo_row(name, repo) %}
| {{ name }} | {{ repo.description }} | {{ repo.tech | join(sep=", ") }} | {{ repo.branch }} |
{% endmacro %}

{# Use the macro #}
{% for name, repo in repos %}
{{ self::repo_row(name=name, repo=repo) }}
{% endfor %}

{# Whitespace control — trim with minus sign #}
{%- if condition -%}
  trimmed output
{%- endif -%}
```

**How kimono uses Tera:**

Templates are embedded in the Rust binary and rendered at runtime with context from the parsed config:

```rust
use tera::{Tera, Context};

fn generate_claude_md(config: &WorkspaceConfig) -> Result<String> {
    let mut tera = Tera::default();
    tera.add_raw_template("claude_md", include_str!("../templates/claude_md.tera"))?;

    let mut ctx = Context::new();
    ctx.insert("workspace", &config.workspace);
    ctx.insert("repos", &config.repos);

    tera.render("claude_md", &ctx)
}
```


## 3. Config Format

File: `.kimono/config.yml` inside the `.kimono/` directory at workspace root.

```yaml
# .kimono/config.yml
workspace:
  name: my-platform
  apps_dir: apps              # Default: apps
  worktree_dir: .worktrees    # Default: .worktrees

repos:
  backend:
    remote: git@github.com:myorg/backend.git
    branch: main              # Default branch to track
    description: "NestJS GraphQL API"
    tech: [nestjs, typescript, graphql, postgresql]
    package_manager: yarn
    depends_on: []
    commands:
      dev: yarn dev
      lint: yarn lint
      typecheck: npx tsc --noEmit
      test: yarn test

  frontend:
    remote: git@github.com:myorg/frontend.git
    branch: main
    description: "Next.js web application"
    tech: [nextjs, react, typescript]
    package_manager: pnpm
    depends_on: [backend]     # Types/API depend on backend
    commands:
      dev: pnpm dev
      lint: pnpm lint
      typecheck: pnpm typecheck

  mobile:
    remote: git@github.com:myorg/mobile.git
    branch: main
    description: "React Native mobile app"
    tech: [react-native, expo, typescript]
    package_manager: pnpm
    depends_on: [backend]
    commands:
      dev: pnpm start
      lint: pnpm lint

  infra:
    remote: git@github.com:myorg/gitops.git
    branch: main
    description: "GitOps infrastructure (Helm, ArgoCD)"
    tech: [kubernetes, helm, argocd]
    depends_on: []
    commands: {}

claude:
  dispatch: true              # Generate agent dispatch in root CLAUDE.md
  agents: true                # Generate .claude/agents/ per repo
  skills: true                # Generate .claude/skills/ per repo
  context_style: detailed     # minimal | standard | detailed
```

### Config Schema Rules

- `repos` keys are the canonical short names used everywhere (CLI args, worktree paths, agent names)
- `remote` is required. Everything else has sensible defaults.
- `branch` defaults to `main`
- `depends_on` references other repo keys. Validated at parse time (no circular deps, no missing refs).
- `commands` is a string-to-string map. Keys are arbitrary but `dev`, `lint`, `typecheck`, `test` are conventional.
- `tech` is a freeform string array. Used in generated context to help Claude understand the stack.

### Minimal Config

The smallest valid `.kimono/config.yml`:

```yaml
workspace:
  name: my-project

repos:
  api:
    remote: git@github.com:me/api.git
  web:
    remote: git@github.com:me/web.git
```

Everything else gets defaults. `kimono init` generates this interactively.

## 4. CLI Commands

### Top-Level

```
kimono <command> [args]
```

### 4.1 Workspace Setup

#### `kimono init`

Interactive wizard that creates a new workspace.

```
$ kimono init
? Workspace name: my-platform
? Where should repos be cloned? (apps): apps
? Add a repo? (y/n): y
? Repo short name: backend
? Git remote URL: git@github.com:myorg/backend.git
? Default branch (main): main
? Description: NestJS GraphQL API
? Tech stack (comma-separated): nestjs, typescript, graphql
? Add another repo? (y/n): y
...
? Clone repos now? (y/n): y
? Generate Claude Code context? (y/n): y

Created .kimono/config.yml
Created .gitignore
Cloned 4 repos into apps/
Generated CLAUDE.md
Generated .claude/agents/ (4 agents)
Generated .claude/skills/ (4 repo dispatchers + 4 workflow skills)
Generated .claude/settings.json
Generated .claude/hookify/ (read-only master rules)
Initialized git repo. Ready to go.
```

What it does:
1. Creates `.kimono/config.yml` from interactive input
2. Creates `.gitignore` (ignores `apps/`, `.worktrees/`, OS files)
3. Runs `kimono clone` to clone all repos
4. Runs `kimono context generate` to create Claude Code files
5. Initializes a git repo and makes an initial commit

Flags:
- `--from <path>` — import from an existing ofmono-style setup (reads `.repos.conf`, converts to `.kimono/config.yml`)
- `--bare` — create `.kimono/config.yml` only, skip clone and context generation

#### `kimono add <name> <remote> [--branch <branch>]`

Add a repo to the workspace.

```
$ kimono add payments git@github.com:myorg/payments.git
Added payments to .kimono/config.yml
Cloned into apps/payments/
Regenerated Claude Code context.
```

Updates `.kimono/config.yml`, clones the repo, regenerates context files.

#### `kimono remove <name> [--delete]`

Remove a repo from config. `--delete` also removes the clone from `apps/` and any worktrees.

### 4.2 Repo Management

#### `kimono clone [repos...]`

Clone repos from config into `apps/`. Skips repos that are already cloned.

```
$ kimono clone              # Clone all
$ kimono clone backend web  # Clone specific repos
```

#### `kimono sync [repos...] [--fetch-only]`

Fetch and rebase all repos to their configured default branch.

```
$ kimono sync
  backend   ✓ up to date
  frontend  ✓ pulled 3 commits
  mobile    ✓ up to date
  infra     ⚠ dirty working tree (skipped)
```

- Operates on `apps/` clones only (not worktrees)
- Skips repos with dirty working trees (warns)
- `--fetch-only` fetches without rebasing

#### `kimono status [repos...]`

Shows the working tree state of all repos — behaves like `git status` but across repos. Local-only, no network calls.

```
$ kimono status
my-platform (4 repos, 3 active worktrees)

apps/backend/ (main)
  nothing to commit, working tree clean

apps/frontend/ (main)
  nothing to commit, working tree clean

apps/mobile/ (main)
  modified:   src/screens/Home.tsx
  modified:   src/api/client.ts

apps/infra/ (main)
  nothing to commit, working tree clean

worktrees:
  backend--feature-payments     feature-payments   3 ahead
  frontend--feature-payments    feature-payments   clean
  backend--fix-auth             fix-auth           1 ahead, 2 modified
```

Behavior:
- Shows each repo's working tree state (staged, modified, untracked) — same information as `git status`
- Lists active worktrees with branch, ahead/behind (from last fetch), and dirty state
- No auto-fetch — use `kimono sync` to update remote tracking
- Filter to specific repos: `kimono status backend frontend`

### 4.3 Worktree Management

#### `kimono wt add <repo> <branch> [--new]`

Create a worktree for a single repo.

```
$ kimono wt add backend feature-payments --new
Created .worktrees/backend--feature-payments/
  Branch: feature-payments (new, from origin/main)
```

- `--new` creates the branch from `origin/<default-branch>`
- Without `--new`, checks out an existing branch
- Path: `.worktrees/<repo>--<branch-slug>/`

#### `kimono wt remove <repo> <branch>`

Remove a worktree and optionally delete the branch.

```
$ kimono wt remove backend feature-payments
Removed .worktrees/backend--feature-payments/
? Delete branch feature-payments? (y/n): n
```

#### `kimono wt list [repo]`

List active worktrees.

```
$ kimono wt list
  backend--feature-payments     feature-payments   3 commits ahead
  backend--fix-auth             fix-auth           1 commit ahead, dirty
  frontend--feature-payments    feature-payments   clean

$ kimono wt list backend
  backend--feature-payments     feature-payments   3 commits ahead
  backend--fix-auth             fix-auth           1 commit ahead, dirty
```

#### `kimono wt feature <name> [repos...] [--new] [--remove]`

**The killer command.** Create or remove coordinated worktrees across repos for a cross-repo feature.

```
# Create worktrees for a new feature across backend and frontend
$ kimono wt feature payments backend frontend --new
Created .worktrees/backend--feature-payments/
Created .worktrees/frontend--feature-payments/

Feature 'payments' ready across 2 repos.
  cd .worktrees/backend--feature-payments/
  cd .worktrees/frontend--feature-payments/

# Remove all worktrees for a feature
$ kimono wt feature payments --remove
Removed .worktrees/backend--feature-payments/
Removed .worktrees/frontend--feature-payments/
? Delete branches? (y/n): n
```

When no repos are specified, operates on all repos:

```
$ kimono wt feature payments --new
# Creates worktrees in ALL repos
```

Dependency awareness: if `frontend` depends_on `backend`, the output notes the dependency order.

#### `kimono wt clean [--merged] [--dry-run]`

Clean up worktrees for branches that have been merged or deleted on remote.

```
$ kimono wt clean --merged --dry-run
Would remove:
  .worktrees/backend--fix-auth/        (branch merged into main)
  .worktrees/frontend--old-feature/    (branch deleted on remote)

$ kimono wt clean --merged
Removed 2 worktrees.
```

### 4.4 Context Generation

#### `kimono context generate [--force]`

Generate Claude Code configuration files from `.kimono/config.yml`.

```
$ kimono context generate
  CLAUDE.md                          updated (preserved custom sections)
  .claude/agents/backend/AGENT.md    generated
  .claude/agents/frontend/AGENT.md   generated
  .claude/agents/mobile/AGENT.md     generated
  .claude/agents/infra/AGENT.md      generated
  .claude/settings.json              updated
```

Behavior:
- First run: generates all files from templates
- Subsequent runs: updates generated sections, **preserves user customizations** (see Generated Files section)
- `--force`: overwrite everything, ignore customizations

#### `kimono context diff`

Show what would change if you regenerated context files.

```
$ kimono context diff
CLAUDE.md:
  + Added repo 'payments' to registry
  ~ Updated backend commands (dev changed)
  
.claude/agents/payments/AGENT.md:
  + New file (would be created)
```

#### `kimono context show`

Show what context files exist and their status (generated, customized, missing).

### 4.5 Utility

#### `kimono exec <command> [repos...]`

Run a command in each repo's `apps/` directory.

```
$ kimono exec "git log --oneline -5"           # All repos
$ kimono exec "yarn install" backend frontend   # Specific repos
```

#### `kimono branch <name> [repos...] [--new]`

Create or checkout a branch across repos (in `apps/`, not worktrees). Useful for quick operations that don't need full worktrees.

### 4.6 Git Workflow Commands

These commands handle the commit-to-PR lifecycle across repos. Each is both a CLI command and a generated Claude Code skill (see Section 5.3).

#### `kimono commit [repos...] [--feature <name>] [-m <message>]`

Commit staged changes in worktrees.

```
$ kimono commit --feature payments -m "Add payment processing endpoint"
  backend--feature-payments     ✓ committed (3 files)
  frontend--feature-payments    ✓ committed (5 files)
```

Behavior:
- Without args: finds all worktrees with staged changes, commits each
- `--feature <name>`: commits in all worktrees belonging to that feature
- With specific repos: commits in those repos' active worktrees only
- `-m`: same commit message for all repos. Without `-m`: prompts per repo (CLI) or generates contextual messages (skill)
- Refuses to commit in `apps/` (read-only master enforcement)

#### `kimono create-pr [repos...] [--feature <name>] [--draft]`

Create pull requests for branches in worktrees. Uses `gh pr create` under the hood.

```
$ kimono create-pr --feature payments
  backend--feature-payments     ✓ PR #142 created (https://github.com/myorg/backend/pull/142)
  frontend--feature-payments    ✓ PR #89 created (https://github.com/myorg/frontend/pull/89)

Feature 'payments' PRs:
  backend:  https://github.com/myorg/backend/pull/142
  frontend: https://github.com/myorg/frontend/pull/89
```

Behavior:
- Pushes the branch to remote if not already pushed
- Creates a PR against the repo's configured default branch
- `--draft`: create as draft PRs
- `--feature`: creates PRs for all repos in that feature
- PR description includes cross-repo context (links to related PRs in the same feature)
- Requires `gh` CLI to be installed and authenticated

#### `kimono update-pr [repos...] [--feature <name>]`

Push latest commits and update existing PRs.

```
$ kimono update-pr --feature payments
  backend--feature-payments     ✓ pushed 2 commits, PR #142 updated
  frontend--feature-payments    ✓ nothing to push, PR #89 up to date
```

Behavior:
- Pushes any unpushed commits to remote
- Updates PR description with latest cross-repo links if new PRs were created since
- Shows PR status (checks passing/failing, review state)

#### `kimono pr-review-comments [repos...] [--feature <name>]`

Fetch PR review comments across repos. Designed for AI agents to read and act on feedback.

```
$ kimono pr-review-comments --feature payments
backend PR #142 (2 comments):
  @reviewer1 on src/payments/service.ts:45
    "This should validate the currency code before processing"

  @reviewer2 on src/payments/resolver.ts:12
    "Missing error handling for declined transactions"

frontend PR #89 (1 comment):
  @reviewer1 on src/components/PaymentForm.tsx:78
    "Use the shared currency formatter from utils/"
```

Behavior:
- Fetches review comments via `gh api`
- Groups by repo and PR
- Shows file path, line number, author, and comment body
- When invoked as a skill, the agent can read these and address them directly

## 5. Claude Code Integration

### 5.1 Generated Root CLAUDE.md

The root `CLAUDE.md` is the primary context file. It contains:

1. **Workspace overview** — name, repo count, architecture summary
2. **Repo registry** — table of all repos with description, tech stack, default branch
3. **Dependency graph** — which repos depend on which (from `depends_on`)
4. **Commands reference** — all repos' commands in one place
5. **Agent dispatch rules** — instructions for the root Claude session to route tasks to repo-specific subagents
6. **Cross-repo patterns** — how to handle features that span repos (create worktrees, work in dependency order)
7. **Worktree conventions** — naming, location, read-only master enforcement

Example agent dispatch section:

```markdown
## Agent Dispatch

When a task targets a specific repo, dispatch to a subagent:

- **Backend tasks** → Use the `backend` agent (`.claude/agents/backend/`)
  Work in: `.worktrees/backend--<branch>/` or `apps/backend/` (read-only)
  
- **Frontend tasks** → Use the `frontend` agent (`.claude/agents/frontend/`)
  Work in: `.worktrees/frontend--<branch>/` or `apps/frontend/` (read-only)

For cross-repo features, create worktrees first:
  kimono wt feature <name> <repo1> <repo2> --new

Then dispatch to each repo's agent sequentially, starting with upstream dependencies.
```

### 5.2 Generated Agent Files

Per repo: `.claude/agents/<repo>/AGENT.md`

Contains:
- Repo description and tech stack
- Available commands (dev, lint, test, typecheck)
- Package manager
- Dependencies on other repos
- Working directory instructions (prefer worktree, fall back to apps/)

### 5.3 Generated Skill Files

**Repo dispatcher skills** — per repo: `.claude/skills/<repo>/SKILL.md`

A dispatcher skill that:
1. Identifies the target worktree (or creates one)
2. Launches a subagent with the repo's agent config
3. Routes the task description

**Workflow skills** — generated for cross-repo git operations:

| Skill | File | What It Does |
|-------|------|-------------|
| `/commit` | `.claude/skills/commit/SKILL.md` | Stages and commits changes in the current worktree(s). Generates a contextual commit message if none provided. |
| `/create-pr` | `.claude/skills/create-pr/SKILL.md` | Pushes branch and creates a PR via `gh`. Auto-populates title and description from commits and cross-repo context. |
| `/update-pr` | `.claude/skills/update-pr/SKILL.md` | Pushes latest commits and updates the PR. Reports check status and review state. |
| `/pr-review-comments` | `.claude/skills/pr-review-comments/SKILL.md` | Fetches PR review comments and presents them for the agent to address. The agent reads comments, makes fixes, then uses `/commit` and `/update-pr`. |

These skills wrap the `kimono` CLI commands, so they work identically whether invoked by a human (`kimono create-pr`) or by Claude (`/create-pr`). The skills add AI-specific behavior: contextual commit messages, summarized PR descriptions from diffs, and structured review comment presentation.

### 5.4 Settings

`.claude/settings.json` — configures additional directories and documents required plugins:

```json
{
  "additionalDirectories": [
    "apps/backend",
    "apps/frontend",
    "apps/mobile",
    "apps/infra"
  ]
}
```

The generated `CLAUDE.md` includes a **Required Plugins** section that tells developers (and Claude) which Claude Code plugins to install for full functionality:

```markdown
## Required Plugins

This workspace expects the following Claude Code plugins:

- **hookify** — enforces read-only master pattern and workspace conventions
- **github** — enables PR creation, review comments, and updates via MCP
```

### 5.5 Hooks (via Hookify)

Kimono generates hookify rules rather than raw `.claude/hooks.json`. Hookify provides a more ergonomic authoring and management experience.

Generated rules:
- **Prevent commits to apps/** — the read-only master pattern enforced at the tool level. Any `git commit` targeting a path under `apps/` is blocked with a message directing the developer to use a worktree.
- **Prevent checkout in apps/** — blocks `git checkout <branch>` in `apps/` directories to keep them on the default branch.
- **Auto-format on write** — optional, if the user opts in during init.

The hookify rules are generated into `.claude/hookify/` and referenced from `.claude/settings.json`. If the hookify plugin is not installed, kimono warns during `kimono context generate` and falls back to documenting the rules in CLAUDE.md as prose instructions.

### 5.6 Custom Section Preservation

Generated files use marker comments to distinguish generated vs. user content:

```markdown
<!-- kimono:start:registry -->
(auto-generated repo registry table)
<!-- kimono:end:registry -->

## My Custom Section
(this is preserved across regeneration)

<!-- kimono:start:dispatch -->
(auto-generated dispatch rules)
<!-- kimono:end:dispatch -->
```

`kimono context generate` only touches content between markers. Everything outside markers is user-owned and preserved.

## 8. Out of Scope (v1)

These are explicitly deferred. Not in v1:

- **Multi-AI-tool support** — no AGENTS.md, .cursorrules, .aider.conf generation. Claude Code only. Architecture should allow adding these later, but v1 doesn't build them.
- **MCP server** — tempting but premature. v2 feature.
- **Build orchestration** — not competing with Nx/Turborepo. Each repo builds itself.
- **Package management** — each repo manages its own dependencies.
- **CI/CD integration** — each repo has its own pipeline.
- **IDE plugins** — CLI-first. No VS Code extension.
- **Code intelligence** — no AST parsing, no symbol search, no knowledge graph. Generated context is template-based, not code-aware.
- **Remote/cloud execution** — local CLI only.
- **Windows native support** — works via WSL. Native Windows is a stretch goal.

## 9. Migration from ofmono

`kimono init --from ~/data/work/ofmono` should:

1. Read `.repos.conf` and convert to `.kimono/config.yml`
2. Detect existing `apps/` clones and skip re-cloning
3. Detect existing `.worktrees/` and register them
4. Generate new Claude Code context files (CLAUDE.md, agents, skills)
5. Preserve any custom documentation from `docs/`

This is a one-time migration path. After migration, the workspace is managed by kimono.

## 10. Decisions Log

Resolved questions and design decisions:

| # | Question | Decision | Rationale |
|---|----------|----------|-----------|
| 1 | Short alias (`ki`) | **No** | Not in v1. Users can alias themselves if they want. |
| 2 | Config location | **`.kimono/config.yml`** (directory) | Allows future expansion (templates, cache, state) without cluttering workspace root. |
| 3 | Worktree path format | **`<repo>--<branch-slug>`** (flat) | Flat and scannable. Current ofmono convention, proven in daily use. |
| 4 | Auto-sync on status | **No** | `kimono status` is local-only, like `git status`. Use `kimono sync` explicitly for network ops. |
| 5 | Hook mechanism | **Hookify** | Generate hookify rules. Fall back to prose in CLAUDE.md if hookify plugin not installed. Document required plugins in settings. |
| 6 | Template customization | **Not in v1** | Templates are compiled into the binary. Users customize via marker-based section preservation, not template overrides. |
| 7 | Repo groups | **No** | Keep it simple. Use explicit repo lists in commands. |
| 8 | Tech stack | **Rust** | YAML parsing (serde_yaml), single-binary distribution, clap CLI UX, avoids the bash-to-Rust rewrite. |
| 9 | AI tool support | **Claude Code only** | v1 focuses exclusively on Claude Code (CLAUDE.md, agents, skills, hookify). Architecture allows adding Cursor/AGENTS.md later. |
