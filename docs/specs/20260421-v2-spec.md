# Kimono v2 Spec

> AI Developer Lifecycle (DLC) wrapper for codebases — single repo or multi-repo — with a plug-and-play Claude skill ecosystem.

Supersedes [v1 spec](./20260417-v1-spec.md).

---

## 1. The pivot in one paragraph

Kimono stops being a "multi-repo aggregator that generates AI config via Tera templates in Rust." It becomes an **AI DLC wrapper**: a workspace that wraps 1..N codebases, keeps the wrapped repos themselves untouched, and ships a curated catalog of installable Claude skills. Instead of Rust code generating CLAUDE.md and agents, two skills do the work — a lightweight `bootstrap` skill writes initial scaffolding, and a heavier `discover` skill walks the source tree to enrich that scaffolding with architecture and domain knowledge. Workflow commands that were Rust subcommands in v1 (`commit`, `create-pr`, `update-pr`, `pr-review-comments`) become installable skills so users only pick what they need. The skill catalog lives **inside this same kimono repo** under `skills/` — the Rust binary fetches it via shallow `git clone` into a local cache.

The binary shrinks. The AI layer gets smarter. The wrapped repo stays clean.

---

## 2. What changes vs v1

| Area | v1 | v2 |
|------|-----|-----|
| Scope | Multi-repo only | Single-repo *or* multi-repo (both first-class) |
| Context generation | `src/context/*.rs` + `templates/*.tera` render CLAUDE.md and agents | `bootstrap` + `discover` skills run inside Claude Code |
| Multi-project repos (monorepos inside `apps/<name>/`) | Not handled — one repo = one agent | Detected by bootstrap (light), enriched by discover. One agent per project. |
| `kimono context generate` | Renders templates | Removed (replaced by bootstrap/discover skills) |
| `kimono context diff` | Diffs templates against disk | Removed |
| Workflow commands (`commit`, `create-pr`, `update-pr`, `pr-review-comments`) | Rust subcommands | Installable Claude skills |
| Hookify rule generation | Built into context generation | Separate `hookify-rules` skill |
| Plugin system | None | `kimono plugins` command backed by a skill catalog inside this same repo |
| Agent file layout | `.claude/agents/<repo>/AGENT.md` (subdirs, undocumented in Claude Code) | `.claude/agents/<repo>.md` or `.claude/agents/<repo>--<project>.md` (flat, documented) |
| Init wizard | Writes config, clones, renders templates | Writes config, clones, installs skills, optionally shells out to `claude` to run bootstrap |
| Rust binary | ~all functionality | Workspace ops + git + worktrees + plugin client + shell-out shortcuts |
| Rollout | N/A | Clean v2 break — v1 code paths removed in the same PR (no production users to migrate) |

## 3. What stays from v1

Unchanged unless noted elsewhere:

- Workspace layout: `.kimono/config.yml`, `apps/`, `.worktrees/`, `.claude/`, `CLAUDE.md` at workspace root
- Wrapped repos in `apps/` remain read-only clones on their default branch
- Worktree-based development: `.worktrees/<repo>--<branch-slug>/`
- Git commands: `clone`, `sync`, `status`, `add`, `remove`, `exec`, `branch`
- Worktree commands: `wt add`, `wt remove`, `wt list`, `wt feature`, `wt clean`
- Config schema for `workspace` and `repos` sections
- Tech stack: Rust + clap + serde + dialoguer + console/indicatif + anyhow
- Git operations still shell out to the `git` CLI; GitHub ops still use `gh` where relevant
- Marker-based section preservation: `<!-- kimono:start:section -->` / `<!-- kimono:end:section -->`. The convention carries forward, but the preservation *logic* is no longer in Rust — bootstrap and discover do their own merging when they rewrite files.

Directory structure, worktree conventions, and read-only master enforcement all carry forward from [v1 §5–§6](./20260417-v1-spec.md). The agent file *layout* does not — see §4.7.

## 4. Core concepts introduced in v2

### 4.1 "AI DLC wrapper"

A kimono workspace is an **outer layer** around 1..N codebases. The AI layer (skills, CLAUDE.md, hookify rules, agents, settings) lives at the workspace root — *not* inside any wrapped repo. This means:

- The wrapped repo's git history never gets AI artifact commits
- Detaching a repo from kimono is a no-op on the repo itself (just delete the workspace)
- A repo can be wrapped by multiple kimono workspaces for different purposes without conflict

The physical layout is the same as v1 (wrapped repos in `apps/`, AI layer at workspace root) — the pivot is framing, not relocation.

### 4.2 Single-repo is first-class

`apps/` may contain a single repo. In that mode kimono gives a single codebase monorepo-style AI tooling without modifying the repo itself — a useful setup for individual projects or for adopting AI tooling incrementally.

Multi-repo is the same system with N repos. Config schema, commands, and the skill ecosystem are identical across both modes. The wizard may ask a top-level "single-repo or multi-repo?" at init, but it's a UX hint only — the underlying data model is the same.

### 4.3 Skill registry — inside this repo

The skill catalog lives **inside the kimono repo itself**, under `skills/`. There is no separate `kimono-skills` repo. Hosting in the main repo avoids a second repo to maintain and gives users one place to file issues, fork, and contribute.

Repo layout:

```
kimono/
├── Cargo.toml
├── src/
├── skills/
│   ├── index.json                    # catalog manifest
│   ├── bootstrap/SKILL.md
│   ├── discover/SKILL.md
│   ├── git-commit/SKILL.md
│   ├── create-pr/SKILL.md
│   ├── update-pr/SKILL.md
│   ├── code-review/SKILL.md
│   └── hookify-rules/SKILL.md
└── ...
```

`skills/index.json` is the catalog manifest:

```json
{
  "schema_version": 1,
  "skills": [
    {
      "name": "bootstrap",
      "description": "Initial AI context setup — minimal CLAUDE.md and per-project AGENT.md from config + manifests.",
      "version": "1.0.0",
      "tags": ["init", "context", "setup"],
      "path": "skills/bootstrap",
      "default": true
    },
    {
      "name": "discover",
      "description": "Deep codebase scan that augments CLAUDE.md and AGENT.md with architecture, patterns, and domain vocabulary.",
      "version": "1.0.0",
      "tags": ["context", "analysis"],
      "path": "skills/discover"
    },
    {
      "name": "git-commit",
      "description": "Stage and commit changes in worktrees with contextual messages.",
      "version": "1.0.0",
      "tags": ["git", "workflow"],
      "path": "skills/git-commit"
    },
    {
      "name": "create-pr",
      "description": "Push branch and open a PR via gh, populating title/description from commits and cross-repo context.",
      "version": "1.0.0",
      "tags": ["git", "github", "workflow"],
      "path": "skills/create-pr"
    },
    {
      "name": "update-pr",
      "description": "Push commits and update an existing PR; report check and review state.",
      "version": "1.0.0",
      "tags": ["git", "github", "workflow"],
      "path": "skills/update-pr"
    },
    {
      "name": "code-review",
      "description": "Fetch PR review comments and structure them for the agent to address.",
      "version": "1.0.0",
      "tags": ["github", "workflow"],
      "path": "skills/code-review"
    },
    {
      "name": "hookify-rules",
      "description": "Generate .claude/hookify/ rules that enforce the read-only master pattern. Depends on the hookify plugin.",
      "version": "1.0.0",
      "tags": ["hooks", "enforcement"],
      "path": "skills/hookify-rules"
    }
  ]
}
```

**Fetch mechanism.** On first `plugins list`/`install`/`update`, kimono shallow-clones the registry repo to `~/.cache/kimono/registry/`. Subsequent commands `git pull` the cache when needed. All skill reads go through the cache.

**Install mechanism.** Installing a skill copies `skills/<name>/` from the cache into the workspace's `.claude/skills/<name>/` and records the version in `.kimono/config.yml > plugins.installed.<name>`.

**Registry URL.** Default baked into the binary: `github.com/sand4rbh/kimono`. Overridable per workspace via `.kimono/config.yml > plugins.registry` so users can fork and point at their fork.

**Versioning.** Each skill carries its own semver in `index.json`. `kimono plugins update <name>` compares the cache's `index.json` version against the recorded installed version and reinstalls if higher. Manual bump in `index.json` when a skill's content changes.

### 4.4 The `bootstrap` skill

The bootstrap skill is the lightweight, fast-running initial setup. It does just enough to give the user a usable starting point — minutes after `kimono init`, the workspace has functional AI context.

**Trigger.** Invoked explicitly by the user in a Claude Code session (e.g. "bootstrap kimono context"), via the `kimono bootstrap` CLI shortcut, or shelled out to from `kimono init`.

**Behavior (skill instructions):**

1. Read `.kimono/config.yml` to learn workspace name, apps_dir, and the list of wrapped repos.
2. For each repo under `apps/<name>/`:
   - Detect whether it is a multi-project repo (look for `nx.json`, `turbo.json`, `pnpm-workspace.yaml`, `lerna.json`, top-level `[workspace]` in `Cargo.toml`, or conventional subdirs like `packages/`, `apps/`, `libs/` with manifests). Detection is file-existence + minimal-parse only — no source-tree walking.
   - If multi-project: enumerate the projects.
   - For each project (or the whole repo if single-project): read its README, manifest, and basic command scripts.
3. Write `CLAUDE.md` at the workspace root covering: workspace overview, repo registry, cross-repo dependencies, agent dispatch instructions, worktree conventions, read-only master guidance.
4. Write one agent file per project at `.claude/agents/<repo>.md` (single-project repo) or `.claude/agents/<repo>--<project>.md` (multi-project) with: description, tech stack, package manager, commands, working directory guidance.
5. Write `.claude/settings.json` with `additionalDirectories` covering each `apps/<repo>/`.
6. Preserve content between `<!-- kimono:start:section -->` / `<!-- kimono:end:section -->` markers — replace only marker bodies, keep user content outside markers intact.
7. Report a summary: files created/updated, any projects where inference was uncertain.

Bootstrap is intentionally cheap — it should complete in seconds and never read deeply into source code. Deep enrichment is the discover skill's job.

### 4.5 The `discover` skill

Discover is the expensive deep scan. It produces real understanding of a codebase by walking the source tree, reading representative files, and inferring architecture, patterns, and domain vocabulary. It runs on demand — typically after the user has worked in the codebase for a while and wants AI context that goes beyond manifest-level detection.

**Trigger.** Invoked explicitly in a Claude Code session ("run kimono discover"), via the `kimono discover` CLI shortcut, or manually when the user wants to refresh context.

**Behavior (skill instructions):**

1. Read `.kimono/config.yml` and the existing CLAUDE.md / agent files (bootstrap must have run first; if not, suggest running bootstrap).
2. For each project (single-project repo or sub-project from the bootstrap-discovered list):
   - Walk the source tree, identify entry points and module boundaries.
   - Detect architectural patterns (DDD, feature folders, event-sourcing, layered, MVC, etc.).
   - Extract domain vocabulary from filenames, type definitions, ADRs, and README content beyond the top section.
   - Identify common workflows (test runners beyond `package.json` scripts, env vars, deployment hints).
   - Map cross-repo or cross-project data flow (shared types, API contracts).
   - Surface hotspots from `git log` (most-changed paths, active areas).
3. Augment CLAUDE.md and per-project AGENT.md by writing into **new marker sections** dedicated to discover output (e.g. `<!-- kimono:start:discover:architecture -->` … `<!-- kimono:end:discover:architecture -->`). Never overwrites bootstrap sections — the two skills compose.
4. Report a per-project summary of what was learned.

Discover is opt-in by default. It costs tokens (lots of file reads) and time. Running it produces a meaningful step-change in agent context quality.

### 4.6 Default skills offered at init

| Skill | Role | Default-install? |
|-------|------|------------------|
| `bootstrap` | Initial AI context setup | Required — always installed |
| `discover` | Deep codebase scan | In default bundle |
| `git-commit` | Commit in worktrees | In default bundle |
| `create-pr` | Open a PR | In default bundle |
| `update-pr` | Push and update a PR | In default bundle |
| `code-review` | Fetch PR review comments | In default bundle |
| `hookify-rules` | Generate hookify rules | In default bundle; hookify Claude Code plugin must be installed separately for the rules to take effect |

The init wizard prompts once with a single Y/n for the default bundle (all six "in-bundle" skills). Bootstrap is installed unconditionally. Users who want a more granular pick can decline the bundle and use `kimono plugins install <name>` afterward.

These are plain Claude skills living in `skills/`. They wrap `git` and `gh` directly and require no kimono CLI calls — kimono is only responsible for installing them.

### 4.7 Multi-project repos and agent file layout

Claude Code only documents one agent layout: flat top-level files in `.claude/agents/<name>.md`. Subdirectory traversal is undocumented. Kimono adopts the flat layout with `--` as a delimiter:

```
.claude/agents/
├── backend.md                  # single-project repo
├── frontend.md                 # single-project repo
├── monorepo--api.md            # multi-project: monorepo/packages/api
├── monorepo--web.md            # multi-project: monorepo/packages/web
└── monorepo--shared.md         # multi-project: monorepo/packages/shared
```

Each file has `name: <repo>` or `name: <repo>--<project>` in its YAML frontmatter — that's the value passed to `Task`'s `subagent_type`. The delimiter `--` mirrors kimono's existing worktree naming convention.

Note: worktrees stay per-repo (`<repo>--<branch-slug>`). Sub-projects inside a worktree are addressed by path, not by separate worktrees.

## 5. CLI changes

### 5.1 New: `kimono plugins`

Alias: `kimono skills`.

```
kimono plugins list [--installed | --available]
kimono plugins search <query>
kimono plugins info <name>
kimono plugins install <name>... [--version <x>]
kimono plugins remove <name>...
kimono plugins update [<name>...]
```

Examples:

```
$ kimono plugins list
Available skills (registry: github.com/sand4rbh/kimono):
  bootstrap        1.0.0  (installed)  Initial AI context setup
  discover         1.0.0  (installed)  Deep codebase scan
  git-commit       1.0.0  (installed)  Commit changes in worktrees
  create-pr        1.0.0  (installed)  Open a pull request
  update-pr        1.0.0                Push commits and update a PR
  code-review      1.0.0                Fetch PR review comments
  hookify-rules    1.0.0                Generate hookify enforcement rules

$ kimono plugins install update-pr code-review
  ✓ Installed update-pr 1.0.0
  ✓ Installed code-review 1.0.0

$ kimono plugins remove code-review
  ✓ Removed code-review
```

### 5.2 New: `kimono bootstrap` and `kimono discover`

Shortcut commands that shell out to the `claude` CLI to run the corresponding skill non-interactively. Useful for regeneration without going through the full init wizard.

```
$ kimono bootstrap
  Shelling out to Claude Code…
  ✓ Wrote CLAUDE.md
  ✓ Wrote .claude/agents/backend.md
  ✓ Wrote .claude/agents/frontend--api.md
  ✓ Wrote .claude/agents/frontend--web.md
  ✓ Wrote .claude/settings.json

$ kimono discover
  Shelling out to Claude Code…
  ✓ Augmented CLAUDE.md (added architecture section)
  ✓ Augmented .claude/agents/backend.md (added domain vocabulary, hotspots)
  ✓ Augmented .claude/agents/frontend--api.md (added patterns, entry points)
```

Invocation form: `claude -p "Run the kimono bootstrap skill for this workspace"` (and similarly for discover). Implementation may refine the exact prompt; the form is non-interactive (no further input expected from the user). If `claude` is not on `PATH`, the command prints an actionable error pointing at the docs.

### 5.3 Removed commands

| Command | Replacement |
|---------|-------------|
| `kimono context generate` | `kimono bootstrap` (or `kimono discover` for deep regen) |
| `kimono context diff` | None (no more template diff semantics) |
| `kimono commit` | `git-commit` skill |
| `kimono create-pr` | `create-pr` skill |
| `kimono update-pr` | `update-pr` skill |
| `kimono pr-review-comments` | `code-review` skill |

### 5.4 Repurposed: `kimono context show`

Friendly status of the AI layer. Prints:

- Workspace name, repo count
- Installed skills with versions (read from `.kimono/config.yml > plugins.installed`)
- Presence/absence of `CLAUDE.md` and each expected `.claude/agents/<name>.md`
- Next-move hints when context is missing:
  - "CLAUDE.md not found — run `kimono bootstrap`"
  - "discover not installed — run `kimono plugins install discover`"
  - "hookify-rules installed but `.claude/hookify/` empty — run discover or invoke the skill manually"

Example:

```
$ kimono context show
Workspace: my-platform (4 repos)

Installed skills:
  bootstrap       1.0.0
  discover        1.0.0
  git-commit      1.0.0
  create-pr       1.0.0
  hookify-rules   1.0.0

Context files:
  CLAUDE.md                              ✓ present
  .claude/agents/backend.md              ✓ present
  .claude/agents/frontend--api.md        ✓ present
  .claude/agents/frontend--web.md        ✗ missing — run `kimono bootstrap`
  .claude/settings.json                  ✓ present

Hints:
  - update-pr skill not installed. Install: `kimono plugins install update-pr`
```

### 5.5 Unchanged commands

`init`, `add`, `remove`, `clone`, `sync`, `status`, `exec`, `branch`, all `wt *` subcommands.

```
$ kimono init my-project
? Mode [single-repo | multi-repo]: multi-repo
? Add a repo? (y/n): y
... (per-repo config, same as v1)

? Clone repos now? (Y/n): y
  [clones repos into apps/]

? Install default skills (discover, git-commit, create-pr, update-pr, code-review, hookify-rules)? (Y/n): y

  ✓ Installed discover 1.0.0

? Run bootstrap skill now to generate AI context? (Y/n): y

  ✓ Wrote .claude/agents/backend.md
```

If the user declines running bootstrap (or `claude` is not installed), `kimono init` prints a hint: "Run `kimono bootstrap` later to generate AI context."

### 5.7 Offline / unreachable registry

- `kimono plugins list --installed` works offline — reads from `.kimono/config.yml` only.
- `kimono plugins list` (without `--installed`) uses the cache if present; otherwise prints a clear error: "Registry cache empty — run with internet to populate."
- `kimono plugins install <name>` uses the cache if present. If the cache is missing, install attempts a shallow clone of the registry first; if that clone fails (no network), install errors out with a clear message.
- `kimono plugins update` always attempts a `git pull` on the cache (or shallow-clones if missing). Fails with a clear error if the network call fails.

## 6. Config schema changes

### 6.1 Remove `claude` section

v1's `claude:` block (dispatch/agents/skills/context_style flags) is removed. Those decisions now belong to the bootstrap and discover skills.

### 6.2 Add `plugins` section

```yaml
plugins:
  registry: github.com/sand4rbh/kimono  # optional; defaults to built-in
  installed:
    bootstrap: 1.0.0
    discover: 1.0.0
    git-commit: 1.0.0
    create-pr: 1.0.0
    update-pr: 1.0.0
    code-review: 1.0.0
    hookify-rules: 1.0.0
```

- `registry` is optional. Defaults to `github.com/sand4rbh/kimono`, baked into the binary.
- `installed` is a map of skill-name → semver string. Installing via `kimono plugins install` updates this map; same for remove/update.

### 6.3 Minimal config (unchanged)

```yaml
workspace:
  name: my-project
repos:
  api:
    remote: git@github.com:me/api.git
```

Defaults for `plugins` are implicit — `bootstrap` is always installed on first `kimono init`.

## 8. Skill content sketches

Full skill bodies live in `skills/<name>/SKILL.md` and follow the descriptive style used by `superpowers`-style skills (explicit "Use when…" trigger, checklists, anti-patterns, dot-graph process flows where helpful). Sketches:

### 8.1 bootstrap

```markdown
---
name: bootstrap
description: Use when a kimono workspace needs initial AI context — fresh init, after adding a repo, or when CLAUDE.md / agent files are missing. Writes minimal CLAUDE.md and per-project AGENT.md from config + manifests.
---

# Kimono Bootstrap

You are setting up the initial AI layer for a kimono workspace. Keep it fast and shallow — discover is the deep-scan companion.

## Checklist

1. Read `.kimono/config.yml`. Extract workspace name, apps_dir (default `apps`), and the repos list.
2. For each repo under `<apps_dir>/<name>/`:
   - Detect whether it's a multi-project repo via file existence: `nx.json`, `turbo.json`, `pnpm-workspace.yaml`, `lerna.json`, top-level `[workspace]` in `Cargo.toml`, or conventional subdirs (`packages/`, `apps/`, `libs/`) with manifests.
   - If multi-project: enumerate the projects (one per subdir with a manifest).
   - For each project (or the whole repo): read its top-level README and manifest. No deep tree-walking.
3. Write `CLAUDE.md` at the workspace root covering:
   - Workspace overview (1 paragraph)
   - Repo / project registry table
   - Cross-repo dependencies (from config's depends_on)
   - Agent dispatch rules (one agent per project, by name)
   - Worktree conventions, read-only master guidance
4. Write one agent file per project:
   - Single-project repo: `.claude/agents/<repo>.md` with `name: <repo>`
   - Multi-project: `.claude/agents/<repo>--<project>.md` with `name: <repo>--<project>`
   Each file contains: description, tech, package manager, commands (dev/lint/test/typecheck if known), working directory (`.worktrees/<repo>--<branch>/`, `apps/<repo>/` is read-only).
5. Write `.claude/settings.json` with additionalDirectories listing each `apps/<repo>/`.
6. Preserve existing content outside `<!-- kimono:start:... -->` / `<!-- kimono:end:... -->` markers.
7. Report a summary: which files created, which updated, projects with uncertain inference.

## Anti-patterns

- Walking source trees beyond top-level manifest reads — that's discover's job.
- Inventing tech stacks not evidenced by manifests or README content.
- Overwriting content outside markers.
```

### 8.2 discover

```markdown
---
name: discover
description: Use when a kimono workspace needs deeper AI context — after working in the codebase, when bootstrap output feels too thin, or when architecture has evolved. Walks source trees and augments CLAUDE.md / agent files with architecture, patterns, and domain vocabulary.
---

# Kimono Discover

You are enriching AI context with a deep codebase scan. Bootstrap must have run first.

## Checklist

1. Read `.kimono/config.yml` and existing `CLAUDE.md` / `.claude/agents/<name>.md` files. If bootstrap hasn't run, stop and tell the user to run bootstrap first.
2. For each project listed in CLAUDE.md's registry:
   - Walk the source tree under `apps/<repo>/<project-path>/`. Identify entry points, module boundaries, public APIs.
   - Detect architectural patterns: DDD, feature folders, event-sourcing, layered, MVC, hexagonal, microservices, etc.
   - Extract domain vocabulary from filenames, type definitions, ADRs (`docs/adr/`, `architecture/decisions/`), and deeper README content.
   - Identify common workflows: test runners beyond `package.json` scripts, env vars, deployment hints, CI config.
   - Map cross-project data flow: shared types, API contracts, message schemas.
   - Surface hotspots: most-changed paths from `git log --pretty=format:'' --name-only | sort | uniq -c | sort -rn | head -50`.
3. Augment CLAUDE.md and per-project AGENT.md by writing into **new marker sections** dedicated to discover output:
   - `<!-- kimono:start:discover:architecture --> ... <!-- kimono:end:discover:architecture -->`
   - `<!-- kimono:start:discover:vocabulary --> ... <!-- kimono:end:discover:vocabulary -->`
   - `<!-- kimono:start:discover:hotspots --> ... <!-- kimono:end:discover:hotspots -->`
4. Never overwrite bootstrap sections. The two skills compose.
5. Report a per-project summary: what patterns were detected, which areas remain unclear.

## Anti-patterns

- Overwriting bootstrap output instead of adding new sections.
- Inventing architecture descriptions not evidenced by the source.
- Reading every file — be selective. Walk the tree, sample representative files.
```

### 8.3 git-commit, create-pr, update-pr, code-review, hookify-rules

Follow the same descriptive structure: frontmatter with explicit "Use when…" trigger, a checklist, anti-patterns, and a brief rationale. Bodies wrap `git` / `gh` / hookify directly. Full bodies are drafted alongside the Rust implementation in the same v2 PR.

## 9. Rollout

Single-PR v2 break. No deprecation phase, no v2.0/v2.1 split — there are no production users to migrate. The same PR:

1. Deletes v1 paths (`src/context/`, `templates/`, `src/cli/context/{generate,diff}.rs`, workflow commands).
2. Adds the plugins system, `bootstrap` and `discover` shortcuts.
3. Adds the 7 default skills under `skills/`.
4. Rewrites the init wizard.
5. Updates `.kimono/config.yml` schema (drops `claude:`, adds `plugins:`).
6. Updates CLAUDE.md and README to describe the new model.

Existing in-tree configs (the v1 test fixtures, the workspace at `~/data/code` that uses kimono) get updated as part of the same change.
